# Safeguards

Use this reference when reviewing a change to a deployed pipeline. Each row identifies the rule to preserve, the point that enforces it, and the failure it guards against. Some rules protect signing authority. Others preserve a build input, a recovery path or the meaning of a published file.

The paths below are relative to the deployed `.github/workflows/` directory. For exact job dependencies and token scopes, see [Workflow contracts](workflows.md). For repository settings and pin values, see [Configuration and pins](configuration.md).

## Rules shared across workflows

| Rule | Enforcement point | What the rule preserves |
| --- | --- | --- |
| Keep the release in two files, with a reusable builder that owns attestation. Project CI calls the same builder. | `release.yml` and `ci.yml`, job `build`, both call `$/.github/workflows/build.yml`. | The builds use the definition at the caller's commit. The attestation names the builder. Separate copies can drift. The self-repository spelling is a convention, with the same commit selection as the relative form for reusable workflows. |
| Start releases only on pushes of `v*` tags. | `release.yml`, `on.push.tags` | Branch pushes and pull requests have no release entry point. The tag filter selects candidates. The origin check authenticates them. |
| Start with `permissions: {}` and grant token scopes per job. | All three workflow headers and job permission maps | A job that loses its map cannot inherit repository write defaults. Both builder callers grant the signing ceiling that GitHub requires for static validation. Each child job declares its own scopes. |
| Keep package builds and third-party verification tools separate from jobs that sign, publish or write releases. | `build.yml` build and signing jobs. Publisher and verifier jobs in `release.yml`, plus `github-release`. | Code handling the package cannot use an OIDC signing or publishing token, or a repository write token. The separate Actions runtime token still permits artifact and cache writes. |
| Pin external actions by full commit SHA. Keep the release version in the comment. | All external `uses:` entries | A moved upstream tag cannot silently change the executed action. The comment identifies the release a reviewer should compare with the SHA. |
| Disable credential persistence on checkout. | `actions/checkout` in `build-sdist`, CI `test` and `origin-check` | Later repository code and collected checkout files do not inherit credentials saved by checkout. |
| Restore no build or tool cache. | Build, CI and release workflows. Each `setup-uv` sets `enable-cache: false`. | A prior job's cache write cannot supply a later release's inputs. Reducing the repository token scopes alone leaves runtime-token cache writes possible. |
| Pass job outputs used in shell scripts through environment variables. Quote them when used as data. | Job and step `env` maps in all three workflows | A producer-controlled filename enters the shell as a value. Direct interpolation into a script can change the script itself. |
| Stop after a failed check. | All steps. No `continue-on-error` or step-level `always()`, `failure()` or `cancelled()` override. | A later step cannot consume files left on disk by a failed download. The two job conditions in `build.yml` handle skipped CI attestations and cancellation across jobs. |
| Serialise releases for the same ref without cancelling an active run. | `release.yml`, `concurrency.group` and `cancel-in-progress: false` | A second run for the tag cannot interrupt the first halfway through an upload. |
| Keep release and builder logic inline or in a pinned action or tool. | `build.yml` and `release.yml`, `run:` and `uses:` | A helper script from the package checkout cannot silently replace a release check. The backend still executes in the designated build jobs. |
| Ignore project uv configuration. | `build.yml` and `release.yml`, `UV_NO_CONFIG=1` | The checkout's `uv.toml` or `[tool.uv]` cannot redirect the build or verification tool's resolution. |
| Use Bash with pipeline failure propagation. | `build.yml` and `release.yml`, `defaults.run.shell: bash` | GitHub runs Bash with `-e` and `-o pipefail`. A successful last command cannot conceal an earlier failure in the same pipeline. |
| Keep shared steps in YAML anchors. Expand only a copy for local tools that require it. | `build.yml` shares attestation steps. `release.yml` shares environment checks, publication steps and verification steps. `tools/expand_anchors.py` handles the local copy. | An edit reaches every consumer of the same check. An expanded copy must preserve the parsed workflow apart from the local self-repository syntax translation. |
| Recompute each consumed file's digest against the producing job's output. | Builder and CI consumers, both publishers and verifiers, and `github-release` | A replacement after production fails even when the uploader supplied matching artifact metadata. A distribution digest describes the backend's output. It cannot establish that the backend is honest. |
| Check changes during development and at deployment with actionlint and zizmor. | Maintainer check outside the release workflow. `tools/quick_checks.py --require-linters` requires both tools. | This catches malformed workflow calls and unsafe permissions or shell substitutions before a release. The quick check narrows the actionlint ignore to the self-repository call. Where that ignore is needed, the expanded copy also needs linting without it to check the call. |

## Build inputs and outputs

In this section the enforcement point is in `build.yml` unless it names project CI. The build lock is the generated, hash-pinned list of the backend's requirements and their dependencies.

| Rule | Enforcement point | What the rule preserves |
| --- | --- | --- |
| Use the same build steps in CI and release. CI sets `attest: false` and tests the installed, digest-checked wheel on tag pushes. Release sets `attest: true` and supplies the tag version. | CI `build` and `test`, release `build`, and `if: inputs.attest` on the signing jobs | CI tests the tagged revision with the release builder. The input keeps signing jobs out of CI even though the caller grants their permission ceiling. Testing from the checkout could hide missing wheel contents. |
| Check out the exact commit, including tags and full history. | `build-sdist`, checkout with `ref: github.sha` and `fetch-depth: 0` | A version derived from Git sees the same history in CI and release. A shallow or different checkout can give it another version. |
| Pin uv and the Python patch version used to resolve and build. | `build-sdist` and `build-wheel`, setup-uv and Python installation | Changes to the resolver or interpreter become reviewable. Implicit runner versions can change the lock or distributions between builds. |
| Reject an existing `build-constraints.txt` in the checkout. Require `build-system.requires` and `build-system.build-backend` and reject `backend-path`. | `build-sdist`, lock generation | A checked-in lock cannot become the release input. An implicit backend or an in-tree backend would escape the declared, externally resolved build requirements. |
| Use the commit's committer timestamp for `SOURCE_DATE_EPOCH` and reject times over five minutes ahead of the runner. | `build-sdist`, lock generation. `build-wheel` receives the timestamp as a job output. | Both builds receive the same time input. A future commit date cannot move the dependency cutoff arbitrarily far forward. |
| Resolve the declared build requirements under the configured cooldown. Require a non-negative integer. Warn on zero and on each qualifying exact pin inside the cooldown. | `build-sdist`, lock generation, `--exclude-newer` and the per-package exemption | A newly uploaded dependency cannot enter the build solely because time passed since the commit. A pin exemption applies only to the named package. |
| Generate hashes from wheels with the pinned Python target and `uv pip compile --no-build`. Omit generated headers and annotations. Write the untracked lock at the project root and record `lock-sha256` in that step. | `build-sdist`, lock generation | The lock has a stable path and content independent of runner paths. With wheel-only resolution, no build dependency runs before the digest exists. Allowing a source build here is a documented reversal. |
| Build the sdist with the generated constraints and `--require-hashes`. | `build-sdist`, sdist build | Even a declared build dependency must match a permitted hash. An unconstrained build can resolve different dependencies after the lock is generated. |
| Require exactly one sdist, with an identical lock under its top directory. Compare its `PKG-INFO` version with any non-empty `expected-version`. | `build-sdist`, sdist checks | Missing lock contents and an accidental tag/version mismatch fail before distribution. These checks follow backend execution. |
| Publish the sdist filename and digest as outputs and upload the named sdist alone. | `build-sdist`, sdist checks and artifact upload | The consumer has an expected filename and digest independent of the transferred file. A checksum shipped only inside the same artifact would not bind the handoff. |
| In separate signing jobs, check each subject against its producer's output before attesting. Use `create-storage-record: false`. Hash and upload each named Sigstore bundle separately. | `attest-sdist`, `attest-wheel`, `attest-sbom`, shared `attest-steps` | Each signature covers the intended subject without granting the backend signing authority or the signer artifact-metadata write access. Bundle outputs let the release check the signature files themselves. |
| Check the sdist digest and, on an attested build, verify its build attestation before building the wheel. | `build-wheel`, sdist checks | A valid signature from another workflow, ref or commit cannot substitute for this repository's builder. Verification also excludes self-hosted runners. |
| Extract the lock from the sdist and compare it to the original lock output before running the backend. Build the wheel from the sdist alone with `--require-hashes`. | `build-wheel`, wheel build, without checkout | The sdist must contain its build inputs. A lock altered during the sdist build cannot substitute for the lock recorded during resolution. |
| Require one wheel. Export its name and digest and upload that file under `wheel`. | `build-wheel`, `Outputs` and artifact upload | CI, the publisher and the wheel signer can all identify and check the same file. A second wheel makes the selection ambiguous. |

## Software bill of materials

| Rule | Enforcement point in `build.yml` | What the rule preserves |
| --- | --- | --- |
| Generate the SBOM in a job with `permissions: {}`, after checking both distribution digests. | `sbom`, download and digest checks | The SBOM refers to these two files. The SBOM tool and code in its temporary environment hold no signing or publishing authority. |
| Generate reproducible CycloneDX 1.6 JSON from the embedded build lock and the wheel's metadata. Use the pinned `cyclonedx-bom` and tool resolution cutoff. | `sbom`, SBOM generation | The inventory describes the shipped package's requirements and locked build components. Using a fresh resolution or unpinned tool could describe a different environment. |
| Obtain declared licences from a temporary environment containing the hash-checked build-lock wheels and the package wheel, installed without their dependencies. Match licences by canonical package name. | `sbom`, licence collection | Build components retain their lock hashes and gain their declared licences where available. An unrelated installation could supply a different version's licence. |
| Include both distribution hashes on the root component. Mark locked build components `scope: excluded` with `release-pipeline:scope=build`. Preserve each runtime requirement as `release-pipeline:requirement` without assigning a resolved version or licence. | `sbom`, CycloneDX assembly | Consumers can distinguish build tooling from what a user must install. An unresolved requirement alone cannot establish the version or licence a user receives. |
| Upload `sbom.cdx.json` as its own artifact with a digest output and separate attestation. | `sbom` output and upload, then `attest-sbom` | The release can verify and distribute the inventory independently. Embedding it in either distribution would also change that distribution's digest. |

## Origin and repository protections

| Rule | Enforcement point | What the rule preserves |
| --- | --- | --- |
| Validate the canonical public PEP 440 version after the leading `v`, with no local part. Derive the prerelease flag from that spelling. | `release.yml`, `origin-check`, tag validation | The build compares the public version literally. Malformed or ambiguous spellings cannot select another version or release status. |
| Use a sparse checkout of `.github`, with full Git history, and execute no checked-out project code. | `origin-check`, checkout and Git inspections | The job can inspect tag objects and ancestry without trusting executable content in the tagged project. |
| Require an annotated tag whose signed internal tag name equals the ref name and whose peeled commit equals `github.sha`. | `origin-check`, tag object check | The signed object authorises this release name and this commit. A valid signature on a different tag name does not suffice. |
| Require the commit to be an ancestor of the current default branch. Protect that branch's workflow and signer changes in repository settings. | `origin-check`, `git merge-base --is-ancestor`; branch protections outside the workflow | Unmerged history cannot be released. Ancestry alone does not establish which people reviewed a commit. |
| Read the signer files from the default branch. Require the exact allowed filenames and a matching repository variable, `RELEASE_SIGNERS_SHA256`, with a digest for each file. | `origin-check`, signer-file comparison | Editing only the files or only the variable breaks the match. Independent control requires separate authority over the two values. Repository variables are writable by some non-admin users. [Signer configuration and authority](configuration.md#release-signers) |
| Select SSH or OpenPGP from the last signature armour header. Set the verifier programs and SSH allowed-signers path explicitly. For GPG, import only the pinned keys into a fresh keyring, require `VALIDSIG` and reject expired, revoked, bad or erroneous signatures. | `origin-check`, signature verification | A tag message, runner defaults or keys already present on the runner cannot select an unapproved verifier or signer. |
| Require both environments to use custom deployment policies with only `v*` tags. Require reviewers on `pypi` and disable administrator bypass. | `origin-check` and `publish-pypi`, shared environment check. Admin audit in `tools/repo_settings.py`. | A branch or unrelated tag cannot use the trusted publisher. The workflow rejects `can_admins_bypass: true` but accepts an omitted field. The admin audit requires explicit `false`. |
| Require active tag rulesets covering `refs/tags/v*`, including applicable parent rulesets. Reject exclusions. Require a creation rule and a ruleset containing update, deletion and non-fast-forward restrictions together. | `origin-check`, tag ruleset check | The declared release pattern cannot silently exclude a subset of tags or permit later tag changes through missing rules. |
| Audit who can bypass the tag rulesets. Creation exceptions must be limited to intended release managers. The ruleset protecting existing tags must have no exceptions. | Admin audit and human review of the actors in GitHub settings | The workflow token cannot read bypass actors. A passing origin check cannot confirm that the effective exceptions match the release policy. |
| Require completed, successful CI on the commit. Poll all pages for matching push runs, excluding the release itself. At least one matching run must reference this repository's builder. | `origin-check`, CI poll and `ci-runs` output | The release cannot skip a failed matching run because of pagination or substitute a green run that never called the builder. A same-named branch at that commit can also match. |

## Publication and verification

| Rule | Enforcement point in `release.yml` | What the rule preserves |
| --- | --- | --- |
| Give each index its own publisher job and named deployment environment. Use its registered trusted publisher and no package checkout. | `publish-testpypi` and `publish-pypi`, plus each index's trusted-publisher settings | Each upload requires an identity bound to the intended repository, workflow and environment. Package code does not run alongside publishing authority. |
| Check that the tag still targets the built commit immediately before the publishing sequence. Download only the named sdist and wheel and compare their digests with the build outputs. | Both publishers, shared tag, download and digest checks | A moved ref or replaced artifact cannot silently become the release. Bundles and unrelated files stay out of the upload directory. |
| Apply the hash rule per expected filename. Missing means upload, equal digest means skip, different digest means fail. Treat only HTTP 200 and 404 as valid lookup results. | Both publishers, shared hash rule | A partial upload can resume without replacing matching bytes. Name-only skipping or treating an index error as an empty version would lose that guarantee. |
| Publish only the selected files in `upload/` and only if it contains files. Use the pinned publication action with PEP 740 attestations enabled. | Both publishers, shared publish step | An empty rerun performs no upload. Each newly uploaded distribution carries the publisher statement that verification requires. |
| Stage every release on TestPyPI and verify it before requesting approval for PyPI. Apply the same digest comparison again on PyPI. | Dependencies of `verify-testpypi`, `publish-pypi` and `verify-pypi` | Staging and production must serve bytes matching the same build outputs. A successful upload request alone cannot confirm what the index serves. |
| Require human approval in the `pypi` environment. Re-read both environments' protections after the gate and before publishing. | GitHub environment rules, then `publish-pypi` shared environment check | Removing and recreating an environment can remove its gate. The check can stop the upload when protections are missing. A solo review supplies a deliberate pause. |
| Require an index listing that contains the two exact filenames. Download each by its listed URL and compare build output, index SHA-256 and actual bytes. | Both `verify-*` jobs, listing poll and distribution download | Another file from the same version, inconsistent digest metadata or a stale listing cannot pass. The bounded poll handles a delay before new files appear. |
| Verify GitHub build provenance for both distributions against the repository, builder workflow, source ref and commit, excluding self-hosted runners. Expose `GH_TOKEN` only in this verification step. | Both verifiers, GitHub attestation check | A signed build elsewhere cannot satisfy this identity. Later third-party verification tools do not inherit that step's token variable. |
| Fetch the integrity document for each file. Require at least one bundle. Every publisher must have `kind: GitHub`, the expected repository, `release.yml` and the index-specific environment. Record the document digest before running the third-party signature verifier. | Both verifiers, provenance fetch | A signature associated with another workflow or environment cannot establish this publisher. Later changes to the provenance file cannot pass the final digest check. |
| Verify PEP 740 signatures against the downloaded files and the expected repository. Pin the tool version and its resolution cutoff. Run in a job with read-only scopes and no deployment environment. | Both verifiers, `pypi-attestations verify pypi` after provenance capture | Matching publisher fields alone do not establish signature validity. The verifier's dependencies cannot use a publishing credential. The design still trusts the signature verification tool. |
| Install the wheel from the index under test with its expected hash, `--no-deps` and `--only-binary :all:`. Resolve dependencies separately from PyPI, wheels only by default. Use isolated pip with `PIP_CONFIG_FILE=/dev/null` and finish with `pip check`. | Both verifiers, wheel install and dependency check | The installed package must be the checked wheel. An inherited pip configuration or a staging dependency cannot silently supply the dependency set. Source builds for runtime dependencies are a documented reversal. |
| Keep all verification checks mandatory and in their shared order. Pass only the two production provenance files and their pre-verifier digests to the final job. | Both verifiers, shared steps. `verify-pypi` outputs and conditional `pypi-provenance` upload. | A downstream job can reject a missing or changed production statement. Staging provenance cannot stand in for the production publisher's identity. |

## GitHub release

| Rule | Enforcement point in `release.yml` | What the rule preserves |
| --- | --- | --- |
| Run only after successful production verification. Use only `contents: write`, no checkout, and address the repository explicitly in GitHub CLI or API calls. | `github-release`, job definition and release step | Publishing a GitHub release cannot mask an incomplete production verification. The job neither runs package code nor receives index-publishing authority. |
| Download the seven named artifact directories separately. Copy only the eight expected files after checking each against a non-empty producer digest. | `github-release`, download and asset checks | Each attached distribution, SBOM, Sigstore bundle and production provenance file has its own verified source. Unlisted files in downloaded directories are never copied. [Asset names and digest outputs](workflows.md#github-release-assets) |
| Reject multiple visible releases for the tag and unexpected assets on an existing draft or published release. | `github-release`, release lookup | A published release cannot carry a lookalike extra asset and still pass. The initial count can detect visible duplicates only. |
| Preserve a prepared draft's notes or start a new draft with an empty body. | `github-release`, draft creation and reuse | Notes remain editable administrative text. Treating the notes as signed would give readers a guarantee the signature checks never make. |
| Upload to a draft, recheck the tag target, then read the draft back by ID. Require exactly the expected names and matching digests before publishing that ID. | `github-release`, draft upload, tag check, asset readback and publish | If a tag-based upload selected another draft, the intended draft fails the readback. A check by tag name alone would not establish which draft will become public. |
| On an already published release, compare every asset digest before accepting a rerun. | `github-release`, published-release branch | A rerun cannot report success for missing or changed assets, or overwrite the release to make it pass. |
| Set `make_latest=false` for prereleases and `make_latest=legacy` for final releases. | `github-release`, draft publication | A prerelease cannot claim “latest”. GitHub uses its legacy selection for finals, including a patch to an older release line. |
| When GitHub reports an immutable release, require `gh release verify` on fresh publication and reruns. Bound each call by the time left in the 300-second deadline and fail on exhaustion. | `github-release`, immutable-release verification with the job token | Asset comparison alone cannot establish successful verification of GitHub's release attestation. Retries retain the same identity, log their times and do not repeat publication. |

## Supported exceptions

The template has two documented reversals. A build dependency available only as a source distribution can require source resolution and a corresponding change to the SBOM licence environment. That dependency then runs before the lock digest exists. A runtime dependency available only as a source distribution can require a source build during the dependency install. That build then runs in the verification job, after provenance capture.

The staging comparison of CI wheel bytes is an optional step, enabled by default. It hashes the downloaded wheel from each qualifying CI run outside the upload directory. Removing it for a non-reproducible build gives up the claim that CI tested the released bytes. CI on the tagged commit still has to pass.

Project-specific choices such as test commands, the build backend, supported test versions and release managers are adaptations. The two reversals and the optional comparison require reviewed workflow edits. The only project release setting read from `pyproject.toml` is the build cooldown. [Configuration and supported workflow edits](configuration.md#project-ci-and-supported-workflow-edits)
