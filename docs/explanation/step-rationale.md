# Why each step exists

Suppose an upload stops after TestPyPI accepts the source distribution but before it receives the wheel. The next attempt needs to answer two questions. Does the file already there match the build? Can the workflow account for who built and published it? A matching filename answers neither. This distinction runs through the pipeline. Hashes identify bytes, signatures identify the workflow or person behind a statement, and a human reviewer decides whether the staged release can go to PyPI.

The [release architecture](architecture.md) shows how the jobs fit together. The [workflow contracts](../reference/workflows.md) give their exact inputs and permissions.

## What the signer authorised

A `v*` tag push starts the release. The filter is deliberately broad enough to include prereleases. The first step narrows it to a canonical public version such as `v1.4.0rc2`. That gives later jobs a version they can compare directly with package metadata and tells GitHub whether to mark the result as a prerelease.

The origin job checks out the Git history with a sparse working tree limited to `.github/`. It needs Git objects to inspect the tag and establish ancestry. It has no reason to execute anything from the package. An annotated tag contains its own name and target. The job checks the embedded name against the ref that started the run, peels the tag to a commit and compares that commit with the run's SHA. It also checks that the commit belongs to the default branch's history. Together those checks bind the signature to the requested version and the commit the builder will receive. Ancestry alone says nothing about who reviewed that commit.

The verifier takes its authorised public keys from the current default branch. That allows the project to remove a retired signer even if older source trees still name that signer. Both the filenames and the bytes must match the checksums in `RELEASE_SIGNERS_SHA256`. This detects a change on only one side. Ordinary repository collaborators can have permission to change that Actions variable. Independent approval therefore depends on who can also change the files on the default branch. [Release signer configuration](../reference/configuration.md#release-signers)

Git verifies an SSH signature against the project's allowed-signers file. For OpenPGP, the job starts with an empty keyring and imports the project's keys. It requires a valid signature. An expired signature or a revoked signing key still causes the check to fail. Explicit program names and key sources keep the runner's Git configuration out of that decision. The last signature header selects the format so ordinary quoted text in the tag message cannot select a different verifier.

## Why the origin job calls GitHub

A trusted publisher on a package index recognises a workflow filename and an environment. The repository supplies the tag restriction. Both environments must admit only `v*` tags, including staging, since a TestPyPI upload also consumes a release filename. The production environment must name a reviewer and disable administrator bypass. These settings can change independently of the tagged commit. GitHub can even recreate a missing environment without its old protection rules. The workflow therefore reads the current settings. It rejects an explicit `can_admins_bypass: true`; the administrator's deployment audit additionally requires an explicit `false`.

The tag rules establish who can create a release ref and what prevents an existing ref from changing. The origin check includes inherited active tag rulesets and rejects exclusions on rulesets targeting `refs/tags/v*`. It looks for creation restrictions and for protection against updates, deletion and force-push together. Only an administrator's audit can establish whether the bypass lists grant the intended exceptions. The workflow token cannot see those lists.

CI runs independently of the release, so the release cannot use a job dependency to wait for it. After the cheaper origin checks pass, the workflow polls all pages of push runs for the commit and tag name, excluding its own run. A completed unsuccessful run stops it immediately. Success requires every matching run to finish successfully and at least one to reference the project's builder. Checking that reference frees each project to name its CI workflows. The API's branch-name field can also match a branch with the tag's name at the same commit. Its run can delay or block the release. The poll has a deadline so missing CI cannot leave it waiting indefinitely.

## Why CI and release use one builder

With two build recipes, a green test run could describe a different package from the one being published. CI and release therefore call the same reusable workflow from their own commit. The CI test job checks out the tests, downloads the wheel, and checks its digest against the builder's output. It uses uv to install that file in a fresh environment for each test Python. The example removes the source tree before running pytest. A module omitted from the wheel must not pass its tests merely because it remains importable from the checkout.

The release call adds the expected tag version and requests attestations. Keeping the attestation jobs inside the builder makes the builder workflow identifiable in their signatures. GitHub checks the permissions requested by a called workflow even for jobs it will skip. Both callers therefore grant the ceiling needed for signing. CI sets `attest: false` to skip those jobs. Each executed job has its own narrower permissions. The wheel job's dependency condition accommodates the intentionally skipped signing job in CI while requiring it to succeed in a release.

## Why the source distribution carries a lock

The sdist job checks out the exact commit with its tags and full history. A versioning backend can then derive the same project version that CI saw. The job installs the pinned uv and Python because the resolver and interpreter both affect which build requirements it can select. It rejects a pre-existing lock file before writing anything. Overwriting a tracked file would also dirty the checkout for backends that incorporate Git state into the version.

The builder requires an explicit backend and build requirements, excludes in-tree backends, and resolves those requirements into a lock containing versions and hashes. This prevents an implicit fallback to a different backend. The committer timestamp gives compatible backends a repeatable build time and gives the dependency cooldown a fixed reference point. Building the same commit tomorrow should not automatically admit another day's releases. The future-date check limits how far the commit can advance that clock. A recent, exact direct requirement can receive a named exemption, so selecting that version is visible in both source and build output.

By default the resolver accepts wheels only. It can compute the lock digest before a build dependency runs. That ordering matters more than the location of the file. The next job needs an expected digest recorded independently of the backend that will package the lock. Allowing source-only build requirements changes this property, since resolution can then run a dependency's own build. The lock omits generated annotations and headers so machine-specific comments do not travel in every sdist.

The sdist build enforces the hashes during installation of its build dependencies. Afterwards the job checks for exactly one archive, checks its embedded lock against the generated file and, on release, checks the version in `PKG-INFO`. These checks catch packaging mistakes, such as an include rule that omitted the lock. They take place after the backend has run. They cannot vouch for the backend's honesty. The job uploads the sdist and passes its name and newly computed digest as job outputs.

## Why signing and wheel building use fresh jobs

The sdist signing job downloads the archive and checks its bytes against the build output before `actions/attest` signs its digest. The wheel and SBOM signing jobs reuse exactly these steps with their own file and digest. Each signing job needs an identity token and permission to write attestations. It executes no package code and requests no extra permission to create an unused storage record. It names the resulting Sigstore bundle after its subject, records the bundle's own digest and uploads it separately. Otherwise the final release could check the package while losing track of which bundle goes with it.

A wheel built from a checkout can work even if the sdist is missing a source file. The wheel job therefore receives only the archive and the builder's outputs. It checks the archive digest and, on release, verifies the GitHub attestation for this builder, ref and commit on a GitHub-hosted runner. It installs the pinned uv and Python, extracts the lock and compares it with the earlier lock digest before the backend runs again. It then builds with the same timestamp and requires hashes for the locked dependencies. Finally it requires one wheel, records its name and digest, and uploads that file for other jobs. This establishes that the shipped sdist supplied the inputs for this wheel. It does not promise that every future build will reproduce it.

## Why the SBOM uses two views of the packages

The software bill of materials (SBOM) describes what went into this particular release. Its job downloads both distributions and checks their digests before reading their contents. The lock inside the sdist records build dependencies and their hashes. The wheel supplies the package metadata that installers will see, including its version and the requirements it declares at runtime.

The first CycloneDX pass reads the lock in requirements mode. That preserves hashes but does not read licences from package metadata. A second pass reads an isolated environment containing the hash-checked build wheels and the project's wheel, installed without resolving additional dependencies. The job joins declared licences to lock entries and the root package by normalised package name. A general merge by CycloneDX component reference could duplicate the same package across the two reports. The tool runs in a job with no repository permissions because inspecting an installed environment can start its interpreter and execute startup hooks.

The job marks build requirements as build-only and preserves runtime requirement strings. An application that installs the library will resolve its own runtime versions, so this SBOM cannot identify the licences of those installed versions. The root component records both distribution hashes. Reproducible CycloneDX output reduces incidental differences, and a separate SBOM digest, artifact and attestation let a reader verify the document without changing either distribution. The utility that generates the SBOM still determines what it says.

## Why staging compares wheels before it uploads

Before each index upload the publisher reads the current tag target through the GitHub API. This catches a ref that moved since the origin check. The publisher needs no checkout. It downloads the two distributions and verifies each against its build digest. The signing bundles stay separate because the publishing action uploads the contents of the directory it receives.

By default, staging also downloads the wheel artifact from every qualifying CI run and hashes the wheel file itself. The artifact service's recorded digest comes from the uploader and describes an artifact archive. Only a comparison of the actual wheel bytes answers whether CI and release produced the same wheel. The comparison files stay outside the upload directory. This check happens once, before staging. Production uses the same release build digests. Projects whose wheels differ across builds can remove the optional check, at the cost of the claim that CI exercised the released bytes.

Each index has its own record of which files exist. For each expected filename, the publisher compares the index digest with the release file's digest. An identical file needs no upload, a missing file goes into the upload directory and a different file stops the job. An indeterminate index response also stops the job. A filename-only skip would treat an unrelated wheel as a successful upload. Per-file decisions allow a rerun to finish a partial upload without replacing files. If there is anything to upload, the pinned publishing action uses the environment's short-lived identity and explicitly requests PEP 740 attestations.

## Why each index is verified from the outside

An upload response cannot establish what an installer will receive. A separate job uses the pinned Python and uv and waits for the index to list both expected filenames. Backoff accommodates a delay in the listing without turning a missing file into an indefinite wait. For each file it checks the build digest against both the index's advertised digest and the downloaded bytes. It then verifies the GitHub build attestation against the expected workflow, tag and commit, excluding self-hosted runners. The GitHub token is made available to that step alone.

The verifier fetches each distribution's PEP 740 provenance from the same index. It requires a nonempty set of bundles, checks that the publisher records identify this repository, `release.yml` and the expected environment, and records the provenance file's digest. Then `pypi-attestations` checks the signatures against the downloaded distribution. The ordering keeps the provenance digest outside the verification tool's control. A defect in the tool can still affect its signature verdict.

Installation answers a different question again. In a clean environment, pip installs the exact wheel from the index under test, by hash and without dependencies. A second invocation resolves the installed package's dependencies using PyPI alone, so an unrelated TestPyPI project cannot supply one. Isolated mode and disabled configuration files keep machine and user index choices out of the test. Wheels-only dependency installation avoids source builds by default. The final `pip check` checks dependency consistency. The project's actual tests already ran in CI. Starting pip again inside the environment can execute Python startup hooks installed by a wheel. The verifier therefore still needs its own job without publishing credentials. [Python startup behaviour](https://docs.python.org/3.14/library/site.html)

Only the production verifier uploads the two provenance files for the GitHub release, which checks them against the digests recorded earlier.

## Why approval comes after staging

By the time the reviewer sees the approval request, the workflow has checked the bytes and provenance served by TestPyPI and installed the staged wheel. Approval lets the production job start. Its first step reads both environment configurations again, because someone could change them while the release waits. That check examines the current configuration. It cannot reconstruct who approved an earlier deployment. For a solo maintainer the gate supplies a deliberate pause. Independent review requires another eligible person and a policy that prevents self-review.

Production repeats the tag, digest and per-file index checks against PyPI. Staging success cannot establish what already exists on another service. Production verification repeats the same checks against bytes and provenance actually served by PyPI. A rerun can recognise an identical file, but matching bytes alone do not repair absent or incorrect provenance. This is why completing a partial upload and accepting its verification are separate decisions.

## Why the GitHub release is published last

The GitHub release collects the verified distributions and the evidence needed to inspect them. It has the only job token with permission to write repository contents. It needs no checkout. It downloads the build outputs, attestation bundles and production provenance, selects the eight expected files and checks each against its producer's digest before copying it into the asset set.

The job looks for a release under the tag before creating one. It rejects multiple visible matches and unexpected existing assets. If there is a prepared draft, its notes belong to the maintainer. If a draft must be created, its body starts empty. Release notes remain editable and carry no signature, even on an immutable release. A signature on the tag cannot authenticate the current contents of that body.

A draft lets the job assemble the assets before making them public. Uploads select the draft by tag, but GitHub's release list can omit a second draft. After the upload the job checks that the tag still points at the built commit, reads the intended draft back by its numeric ID and compares the entire asset set with the local names and digests. That last read establishes what the job is about to publish even if the initial list was incomplete. Prereleases never become “latest”. Finals use GitHub's legacy selection so a later patch on an older release line need not displace a newer major version.

A rerun that finds a published release compares the asset digests and leaves identical assets and notes in place. If GitHub marks that particular release immutable, the job must also verify GitHub's release attestation. Both the fresh and already-published paths reach this check. Otherwise an unsuccessful first verification could become a successful rerun merely because the assets now exist. The job retries verification with the same token within a five-minute budget, limits each invocation to the time remaining and records the attempt times. Exhaustion leaves a failed verification to investigate. It does not trigger another publication. The deadline bounds the job's wait. The service can take longer.

## Why the same safeguards appear in several files

GitHub Actions artifacts carry files. Job outputs carry the expected digests separately. A job with no repository scopes can still write artifacts and caches through its runtime token. Producers therefore name and hash what they hand off, consumers compare the actual bytes, and the workflows never restore caches. A failed download can leave extracted files behind. No later step in that job may use them. Bash pipeline failure propagation and stopping on check failures make this rule apply inside shell steps too.

Workflow-level permissions start empty. Each job requests what it needs. Checkouts avoid leaving a Git credential on disk, and shell steps receive filenames and other outputs through environment variables rather than as interpolated shell source. The trusted checks live in the workflow itself, so changing a script in the package checkout cannot replace one. Release concurrency is grouped by tag, with in-progress cancellation disabled. A later request for the same tag must not interrupt a publication already in progress.

Action references use full commit SHAs because a movable tag would change the code that runs. Python and uv use explicit versions. For the two independent Python tools, an exact version and a fixed upload cutoff constrain resolution without introducing a second build lock. A change to that date can change the transitive packages. The tools still depend on the integrity of files served by PyPI. Disabling uv's project configuration keeps a package's local resolver choices out of the release workflow. [Configuration and pins](../reference/configuration.md)

The repeated attestation, publisher and verification steps are YAML aliases. In particular, production reuses the environment check from the origin job. This keeps a correction to a shared check from landing in staging alone. For local tools that need it, an expanded copy preserves the shared step bodies. [Safeguards](../reference/safeguards.md) gives the enforcement point and cost of removal for individual controls. [Trust and limits](trust.md) explains what can still go wrong when those controls all pass.
